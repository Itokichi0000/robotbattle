## 次の優先タスク（次セッションはここから）

1. **会場での人間プレイテスト**：通りがかりの人が説明なしで「選ぶ→チャージ→パンチ」まで行けるか、所要時間、迷う箇所を記録。
   1発の値段・チャージ額・必殺/ピンチの数値を BALANCE_REPORT と比べて再調整（DECISION_LOG に記録）。
2. **人数差**：シミュレーションでは 10対6 だと少ない側のラウンド勝率が数%。少人数側の離脱が実際に起きるか観察し、
   必要なら「人数の少ないチームのパンチ強化（最大×2、オプション・デフォルトOFF）」を検討（偽プレイヤーで悪用されないよう、
   人数は“直近にパンチした人数”で数える）。
3. 実機確認：スマホ2〜3台 + 会場PC（GPU）で `pnpm start`、遅延と FPS を TEST_PLAN に記録。連打時のフレーム落ちと音の飽和を確認。
4. 3D品質：パンチの打撃感（ヒットストップ・被弾のけぞりの強化）、KO時のスローモーション、地方が塗られる瞬間の演出強化（品質「高」のみブルーム）。
5. Dockerfile + docker-compose（server/web/永続ボリューム）と DEPLOYMENT 手順の検証（公開はしない）。
6. （承認後）LNbits テストウォレットで実決済の少額テスト（105 sats）。

## 既知の課題・リスク

- 人数の多いチームがほぼ勝つ（BALANCE_REPORT §2）。「友だちを呼ぶ」動機にはなるが、少ない側が諦める恐れ。上記2で対応検討。
- 3D性能は GPU 無し環境（約4fps）でしか測れていない。会場GPUで連打時のFPSを要確認。
- 適応HPは「前ラウンドの殴る速さ」から決めるため、人が急に増えた直後のラウンドは短く、急に減った直後は時間切れになりやすい。
- `node:sqlite` は Node の Experimental 機能（警告を抑制して起動）。Node更新時に要確認。
- 旧DB（初版スキーマ）は読み込めない（明示エラー）。既定のDBファイル名を `sats-wars-v2.db` に変更済み。
